# Аудит кодовой базы: качество расчётов и бесплатность модели

**Дата:** 20 октября 2026
**Проект:** «Платформа подбора роботизированных решений» (Team20, ЛЦТ 2026)
**Охват:** 55 JS-файлов, 7 REST-модулей, 197 решений каталога, 3 сценария экономики

---

## 1. Главный вывод

**Модель полностью бесплатна.** Ни одного платного API, SDK или внешнего сервиса:

| Проверка | Результат |
|---|---|
| Зависимости `package.json` | 17 шт., все open-source (express, better-sqlite3, pdfkit, exceljs, puppeteer, three, bcryptjs, jsonwebtoken, xlsx, axios, ffmpeg-static…) |
| Платные AI/облачные SDK | **0** (нет `openai`, `@anthropic-ai`, `langchain`, `google-generativeai`, Stripe и т. п.) |
| Сетевые вызовы в сервисах расчёта | **0** (`require('http'/'https'/'net'/'axios')` отсутствует) |
| Ключи/секреты в коде | только `JWT_SECRET` с дефолтом в `config.js` — **для продакшена обязательно задать через env** |
| «ИИ-рекомендации» | rule-based скоринг (fit + бенчмарки + доменные поправки), внешних вызовов нет |

Итог: платформа работает офлайн на бесплатном стеке; расчётные и рекомендательные
модули не обращаются ни к одному внешнему сервису.

## 2. Что было найдено и исправлено

### 2.1. Критично: экономика модели была абсурдной

**Симптом:** склад 8000 м² / 60 чел. → IRR **497%**, ROI за горизонт **2387%**,
срок окупаемости **0,2 года**. Медицинский объект → ROI **−564%**, не окупается.

**Корень проблемы (3 независимых дефекта):**

1. **Экономия ФОТ не была связана с количеством роботов.** 2 робота «экономили»
   45 млн ₽/год при 57,6 млн ₽/год ФОТ — физически невозможно.
2. **Двойной учёт остаточного ручного труда.** Экономия ФОТ уже измерялась
   относительно базового сценария, а остаточный ФОТ вычитался из неё ещё раз.
3. **OPEX по ТЗ был разобран неверно.** По ТЗ OPEX = сервис + лицензии +
   электроэнергия + материалы + ремонт + управление (остаточного ФОТ там нет).

**Исправление:**

- Новый общий модуль `shared/calc-core.js` (UMD: работает и в Node, и в браузере) —
   единый источник правды для клиента и сервера.
- `computeLaborEffect()`: фактическое сокращение ФОТ ограничено парком
   (`robotCount × 0,9 / staff` — один робот заменяет до 0,9 оператора);
   прирост производительности применяется к **оставшемуся** штату и тоже
   ограничен парком.
- Размер парка учитывает эффект: роботов столько, сколько нужно для заявленного
   сокращения труда — иначе экономия не связана с CAPEX.
- OPEX приведён к формуле ТЗ; остаточный ФОТ показывается как справочная
   величина и в OPEX не входит.
- Доменная коррекция теперь применяется **до** абсолютного потолка калибровки
   (медицина больше не получает двойной штраф 0,15 × 0,25).

**Результат на контрольных сценариях:**

| Сценарий | Было | Стало |
|---|---|---|
| Склад 8000 м², 60 чел. | IRR 497%, ROI 2387% | IRR 58%, ROI 222%, окупаемость 1,6 года |
| Логистический хаб, 120 чел. | IRR 472%, ROI 3208% | IRR 137%, ROI 871%, окупаемость 1,0 года |
| Медицинский объект, 24 чел. | ROI −564%, не окупается | окупаемость 4,6 года, ROI 53%, IRR 12% |

### 2.2. Критично: Excel-экспорт падал с HTTP 500

В ExcelJS 4.4.0 нет `wb.write(res)` — только `wb.xlsx.write(res)`. Исправлено
в обоих маршрутах экспорта.

### 2.3. Критично: кириллица ломала HTTP-заголовки

`Content-Disposition` с русским именем файла → `ERR_INVALID_CHAR` на клиенте.
Добавлен общий хелпер `server/utils/http-headers.js`: ASCII-имя + RFC 5987
(`filename*=UTF-8''…`).

### 2.4. Расхождение клиента и сервера до 98%

Логика расчёта была продублирована в `app.js` и `server/services/calculation.js`.
Вынесена в общие модули `shared/calc-core.js` и `shared/finmath.js`
(IRR/DPP теперь считаются одинаково — раньше клиент их вообще не считал).

### 2.5. Прочие исправления

- **ROI кредитного сценария не учитывал OPEX** — теперь учитывает.
- **Замена оборудования считалась по разным годам в TCO и IRR** — унифицировано
  (кратно сроку амортизации, только внутри горизонта).
- **Окупаемость**: клиент и сервер считали по-разному (0,2 года против −1) —
  приведено к формуле ТЗ с полом 1 год.
- **DPP мог быть меньше срока окупаемости** — добавлен пол 1 года.
- **RaaS**: база аренды — только оборудование, инфраструктура и ПО «исчезали» →
  аренда выглядела заметно дешевле покупки. Теперь база — полный CAPEX решения.
- **Сервис в каталоге был завышен в 3–12 раз**: в 10 демо-решениях 21–36%
  CAPEX/год (95 000 ₽/мес на AMR за 3,8 млн ₽) против 2,5% в 187 позициях
  ФЦ БАС. Приведён к единому ориентиру 2,5% CAPEX/год (эксплуатация ≈ 17,5%
  CAPEX/год — практика автоматизации складов: 12–18%).
- **Предупреждения о реалистичности считались только на сервере** и не
  показывались в UI — теперь выводятся в интерфейсе вместе с оценкой
  достоверности расчёта.
- **Подписи метрик** в UI показывали проценты и годы в рублях («0 ₽ → 269 ₽») —
  исправлено на «0,0 % → 269,2 %».

## 4. Открытые вопросы (не блокеры, требуют решения владельца продукта)

1. **Метрики каталога ФЦ БАС условные.** Во всех 187 позициях одинаковые
   «−35% трудозатрат / +25% производительности» — это заглушки, а не данные
   производителей. Из-за этого по самым дешёвым решениям модель даёт IRR > 100%
   и ROI > 800% (арифметически корректно, но выглядит неправдоподобно).
   Платформа теперь предупреждает об этом («проверьте заявку вендора»), но
   данные стоит обогатить реальными заявками.
2. **`JWT_SECRET` имеет значение по умолчанию** в `config.js` / `config/index.js` —
   перед продакшеном нужно задать переменную окружения.
3. **Медицинские «потолки»** (ROI ≤ 160%, окупаемость ≥ 3 лет) — консервативные
   ограничения по Таблице 1 ТЗ. Они делают ROI не совсем равным NPV в медицинских
   сценариях; при желании их можно заменить явными предупреждениями.
4. **Формула количества роботов** применяет поправку на доступность и
   использование ПОСЛЕ округления вверх (`ceil`, затем деление) — небольшая
   неточность в сторону завышения парка. Не менялась, чтобы не трогать
   согласованный с ТЗ расчёт; при желании легко исправляется.
5. **Детерминированная модель и симулятор** по-разному учитывают инфляцию:
   расчёт — в постоянных ценах, симулятор — помесячно с инфляцией OPEX.
   Это осознанно (иначе инфляция учитывалась бы дважды), но стоит держать в уме
   при сравнении цифр шага 3 и шага 4.
